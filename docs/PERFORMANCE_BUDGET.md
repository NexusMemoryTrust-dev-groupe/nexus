# Performance Budget (SLA) — plan 6.1

> Измерено: 2026-08-11, Windows 11 x64, `cargo run --release --bin nexus_sla_bench`.
> Корпус: 10 000 гетерогенных записей в изолированной temp-БД (SQLite, WAL,
> FTS5, семантический индекс). Пользовательские данные не затрагиваются.

## Метрики и верхние границы

| # | Метрика | SLA (план 6.1) | Измерено | Статус |
|---|---|---|---|---|
| 1 | startup (открытие БД + миграции с нуля) | < 2000 ms | 22 ms | ✅ |
| 2 | insert (сохранение одной записи, среднее) | < 50 ms | < 1 ms | ✅ |
| 3 | search (FTS по корпусу 10k) | < 100 ms | 8 ms | ✅ |
| 4 | cached (повторный build_context из кэша) | < 50 ms | < 1 ms | ✅ |
| 5 | context (полный пайплайн intent→package) | < 200 ms | 106 ms | ✅ |
| 6 | mcp (tools/call round-trip, dispatch) | < 100 ms | < 1 ms | ✅ |
| 7 | index (семантический fingerprint на запись) | < 1000 ms | 12 ms | ✅ |

**GATE: PASS** — все семь метрик укладываются в бюджет с запасом.

## Как воспроизвести

```powershell
cargo run --release --bin nexus_sla_bench
```

Бинарный файл: `src-tauri/src/bin/nexus_sla_bench.rs`. Выходной код
0 = GATE PASS, 1 = FAIL (используется как CI-гейт регрессий, план 6.2).

## Замечания

- `search` использует FTS5 (`memory_fts MATCH`). Гибридный канал
  (cosine + lexical + filename) живёт в `SemanticSearch::search_hybrid`;
  его полный скан по 10k записей занимает ~290 ms — это **не** SLA-путь,
  кэш контекст-пакетов (п. 4) обслуживает повторные запросы.
- `insert` намеренно измеряет среднее по корпусу: отдельная вставка
  с WAL-журналом дешевле 1 ms.
- `mcp` измеряет диспетчерский путь `handle_request_line` (тот же код, что
  stdio-сервер), без оверхеда спавна процесса. Реальный процесс добавляет
  ~30-50 ms на старт, что учтено бюджетом < 100 ms.
- Startup 22 ms — это миграции + инициализация репозитория. Полный запуск
  приложения (Tauri, окно, ONNX-модель в фоне) вне этого замера, но модель
  грузится асинхронно и не блокирует первый экран.
